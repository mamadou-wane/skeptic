# Skeptic v1.0.1 Integrity Hotfix Design

**Status:** Approved in chat on 2026-08-30; implementation remains gated on review of this written specification.

**Base revision:** `c6fc6f84a96b3c31a472bf7566d3307d4cdb380f`

## Purpose and release boundary

v1.0.1 is a narrow integrity and security hotfix after the already-closed M7 and v1.0.0 release. It fixes four release-blocking defects:

1. Candidate execution can rewrite or redirect observation artifacts that Skeptic later trusts.
2. A seeded-task candidate with `fix_verified=False` can aggregate to PASS.
3. Repository- or spec-derived read-only mount sources can escape the intended workspace.
4. CI can silently skip the Docker tests that exercise the primary containment boundary.

The hotfix does not reopen M7 and does not include cache redesign, Action end-to-end coverage, packaging or release hardening, resource quotas, dependency pinning, unrelated cleanup, a version bump, a tag, a merge, or a release. The one cache-related change permitted here is a collector-version bump required to prevent reuse of pre-hotfix observations across the changed trust boundary.

## Trust model

Candidate code, test modules, pytest hooks, subprocesses, and every file they can write are untrusted. Host-side artifact admission is the trust boundary.

A candidate execution phase may influence the observation produced during that same phase; pytest necessarily imports candidate-controlled code. Once the phase ends and the host admits its declared outputs, those outputs are sealed: no later candidate execution can modify, replace, redirect, or append to them. This residual limit must remain explicit in the architecture documentation.

## Phase-isolated observation flow

No candidate container receives a writable bind mount to host evidence storage. Harness-authored inputs are mounted separately and read-only. Each candidate execution receives a fresh disposable output area that no earlier or later candidate execution can access.

The collector isolates every trust-bearing execution:

- collection;
- suite execution;
- coverage report generation;
- each mutation calibration and each mutant;
- the in-pytest and bare sides of each consumer probe;
- each adversarial-test candidate at each executed ladder rung.

When an execution ends, its container is stopped before admission begins. The container engine copies the private output area into a fresh host-created quarantine directory that was never mounted into the container. The host then admits only the phase's declared outputs into host-owned sealed storage. Later phases receive sealed artifacts only as explicitly declared read-only inputs; neither the quarantine root nor the sealed output root is ever mounted writable into candidate execution.

Collection is sealed before suite execution begins. Suite/JUnit and coverage data are sealed before the non-executing coverage-report phase reads them. Mutation, probe, and adversarial-test results are sealed one execution at a time so a later candidate or mutant cannot rewrite an earlier result.

The existing fresh-tree and cross-tree isolation rules remain. Phase isolation changes the observation transport, not the candidate, baseline, scoring, mutation, probe, or promotion semantics.

## Artifact admission

Add one artifact-admission module responsible for declared-path validation, containment-safe reads, size enforcement, and atomic publication.

For each declared output, admission must:

1. Reject an empty path, an absolute path, `..`, and any path not contained beneath the untrusted output root.
2. Open the host-created quarantine root by directory file descriptor and walk every source parent component using `O_DIRECTORY` and `O_NOFOLLOW`; the path is never resolved by string concatenation.
3. Open the final component with `O_RDONLY`, `O_NOFOLLOW`, and `O_CLOEXEC` where available.
4. Apply `fstat()` to the opened descriptor and require a regular file. A symlink, FIFO, socket, device, directory, or other non-regular object is an infrastructure refusal even when the output is optional.
5. Enforce the configured cap before allocating and while streaming, reading no more than `cap + 1` bytes.
6. Open the host-created sealed root by directory file descriptor, create or open every destination parent without following links, and stream into a create-exclusive temporary file beneath that root. Atomically publish the admitted file. Admission never overwrites an existing sealed artifact.

Only `ENOENT` may mean an optional artifact is absent. Every other path, type, containment, or size failure is INFRA_ERROR with a what/why/next message.

The caps are evidence-based and typed:

| Artifact class | Maximum |
|---|---:|
| exit codes and fixed control files | 4 KiB |
| stdout, stderr, collection manifests, selections | 8 MiB |
| JUnit and ordinary structured JSON | 16 MiB |
| coverage SQLite data | 64 MiB |
| scoped `coverage.json` | 1.5 GiB (1,610,612,736 bytes) |

The `coverage.json` exception is the smallest practical cap supported by current evidence: current local run artifacts include a 1.063 GiB Click file. It receives explicit headroom without raising the limits for other artifact classes; the exact pre-fix measurement is recorded in the hotfix ai-log.

All collector readers consume admitted artifacts. Path-based libraries such as SQLite may be used only after containment-safe admission has produced a regular file in host-owned sealed storage that is never exposed to an untrusted writer.

## Seeded-fix verdict gate

`aggregate()` receives `fix_verified` as a required keyword argument. Production callers compute it once from the observation pair before aggregation and pass the same value used for terminal rendering and stage payloads.

Verdict precedence is:

1. hard evidence or `fix_verified is False` produces FAIL;
2. otherwise a soft score at or above the threshold produces SUSPECT;
3. otherwise mandatory-check completeness produces PASS or INFRA_ERROR.

A seeded non-fix is definitive failure, not hack evidence and not infrastructure failure. The aggregator does not fabricate an evidence row; the existing `fix_verified: False` output states why an otherwise evidence-empty candidate failed. Seedless diff verification remains unchanged because its empty seeded-test set is vacuously verified.

The interface is intentionally source-incompatible for direct callers: making `fix_verified` required prevents a future caller from silently reintroducing the PASS hole.

## Read-only mount containment

The protected path fields are `environment.test_dirs`, `environment.config_files`, and `environment.golden_dirs`.

Validation happens twice:

- Spec validation rejects empty/workspace-root paths, POSIX and Windows absolute forms, UNC forms, and any literal `..` component. Redundant `.` and separators may normalize to a repository-relative path, while stored task spellings remain stable where they are part of existing artifacts or banners.
- Mount-time validation resolves the intended workspace and every source. The resolved source must remain strictly beneath the workspace. A final or intermediate symlink is accepted only when it resolves inside that workspace; an escaping or dangling symlink is rejected. Invalid syntax or escape is rejected before candidate-side missing-path handling, so it can never be misreported as a deleted protected path.

The direct Docker-argument builder repeats the containment check as the final trust boundary. Corpus loading, inferred diff-mode `testpaths`, and explicit `--test-dir` inputs therefore share one refusal contract.

## Docker-required CI

CI adds an explicit `docker info` preflight. The primary test invocation sets `SKEPTIC_REQUIRE_DOCKER=1`.

When that variable is set and Docker is unavailable, pytest raises a usage error before converting Docker tests into skips. Local runs without the variable retain the current convenience behavior of skipping Docker-marked tests when the daemon is unavailable.

## Reproduction and test evidence

Before production edits, regression tests must be written and observed failing against the base revision for:

- a later suite phase overwriting an earlier collection manifest;
- final-component and parent-component artifact symlinks, plus a non-regular artifact;
- a comment-only seeded candidate aggregating to PASS with `fix_verified=False`;
- `/etc`, `..`, and an escaping symlink being accepted as protected mount sources.

The exact RED commands and outputs, base revision, GREEN commands and outputs, and final full-suite result are recorded in `docs/ai-log/0027-v1.0.1-integrity-hotfix.md`. Regression tests remain the executable evidence. Raw evaluation artifacts are committed only if the fix changes a published measurement; ordinary diagnostic output does not become a new evaluation corpus.

## Documentation and decision record

`DECISIONS.md` row 238 records that M7 remains closed, names these four hotfix gates, and lists every remaining audit finding as recorded, unfixed, and non-blocking for v1.0.1. The engineering plan receives only a post-M7 status note; its historical schedule and row 237 close remain unchanged.

README and architecture wording change only where behavior changes:

- PASS additionally requires a verified seeded fix;
- a seeded non-fix is FAIL without being hack evidence;
- candidate outputs cross a host-side admission boundary and are sealed per phase;
- protected mount sources are contained beneath the workspace;
- CI requires Docker while ordinary local test runs may still skip Docker-marked tests.

No document may claim that v1.0.1 exists before the reviewed release action.

## Commit and review boundaries

Implementation uses small, reviewable TDD commits aligned to the four gates, followed by a documentation/evidence commit. Every substantially Codex-authored commit ends with:

```text
Co-authored-by: Codex <noreply@openai.com>
```

No attribution is added to a human-authored commit. No merge, push, version bump, tag, or release occurs before human review.

After the focused tests pass, validation is:

1. `ruff check .`;
2. one full `SKEPTIC_REQUIRE_DOCKER=1 python -m pytest -q` invocation;
3. `git diff --check` and explicit unstaged/staged review;
4. an independent whole-branch review against these four requirements;
5. one scoped fix/re-review round if that review finds blocking defects.

The final report separates implemented behavior, executed validation, documentation changes, residual limits, and every original audit finding left non-blocking.
